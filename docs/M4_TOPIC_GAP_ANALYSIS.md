## 2. How the proposal was built

Three rules, applied in order:

1. **Do not assume one topic per item.** Items are merged where their learning
   objectives substantially overlap, and split where prerequisite chains diverge.
2. **Reuse before authoring.** Where a rewritten lesson already teaches the
   material, the topic points at it rather than commissioning a new one.
3. **Keep the dependency honest.** Every prerequisite below carries a reason.

Result: **61 proposed topics for 82 items** — a grouping
ratio of 1.34 items per topic.

**4 of them need no new lesson at all**, because Batch 1 already
taught the material:

| Proposed topic | Reuses | What already exists |
|---|---|---|
| `core.phase` | `01_qubits` | ALREADY TAUGHT: 01_qubits has a dedicated section. This topic needs no new lesson - 01_qubits can be primary. |
| `qiskit.bloch_sphere` | `01_qubits` | ALREADY TAUGHT: 01_qubits has a full Bloch sphere section and 13_classical_bit_vs_qubit has a second. No new lesson needed. |

## 6. Compatibility considerations

**Adding a topic requires a migration.** `app/curriculum.py` is imported only by
migrations, tests and scripts — there is **no runtime sync** from the registry
into the database. Editing `TOPICS` alone changes nothing for a running service;
a new Alembic revision is needed to insert the rows. That revision is a separate
approval from this proposal.

**New topics should be created with `status = "draft"`.** Only `published`
topics appear in learner navigation, so drafting first keeps the roadmap rule
(no inaccessible modules) intact while content is authored.

**No legacy-mastery risk.** New topic IDs have no entry in `FLAT_TO_STABLE` and
no legacy tag rows to inherit, so nothing to migrate and nothing to lose on
downgrade. The 13 existing topics are untouched by this proposal.

**Mastery semantics unchanged.** Confidence stays `high`/`medium`/`low`; only
`high` is mastery-mappable. New lessons should map at `high` to count toward
prerequisites, otherwise the graph will not unlock as designed.

**Prerequisite kinds.** `required` blocks progression, `recommended` only warns.
The proposal uses `required` for genuine dependency and `recommended` for
motivation, so the main track is not gated on optional theory.

**Suggested lesson slugs are placeholders.** The numeric prefix is a convention,
not a requirement; names must not collide with the 13 existing slugs, which are
foreign keys into quiz attempts, challenge attempts, recommendations and chat
history.
